01

READ THE RULES

先理解循环，再理解数字

在比赛页打开“提示 → 简介”。先用一句话解释每一步，再看表格里每一列的含义。

  1. 1果农采集
  2. 2三池法力
  3. 3施法消耗
  4. 4战场变化
  5. 5再次观察
规则表格的含义与不能直接推导的结论
表格中的内容正确理解不能直接推出
魔法 manafire / water / earth 等元素类型它不是法力点数
费用消耗本方对应元素的法力不是对方实际掉血量
法力 / 威力攻击或特殊效果的说明值有盾时仍必定掉同样的血
持续时间界面文档中的时间说明必然等于飞行、冷却或盾的寿命
元素相克火克土、水克火、土克水不区分盾与攻击方向就能下结论
想一想

“这个法术现在能放”，为什么不等于“现在就应该放”？把你的解释留到后续资源争用实验里验证。

02

ASK BEFORE YOU CALL

把问题翻译成接口

下面是历史 JS 接口证据中的入口。方法能读取列表，不代表列表里每个字段都已经验证。

显示 6 个接口
问题、JS 接口与验证边界
我想知道 / 做什么JS 入口使用边界
我有哪些果农？hero.findMyCollectors()对象字段逐项核对，不读取隐藏字段。
我有多少火法力？hero.getTotalMana("fire")查询单池要传元素；无参历史样本是三池之和。
对面有哪些来袭飞弹？hero.findEnemyMissiles()没观察到某类飞弹，不代表它不存在。
果农下一次采哪种水果？hero.chooseItem = function (collector) { return "fire"; }选择回调不是收入保证；完整调度后续再讲。
能否尝试一个法术？hero.canCast(spellName)一次 false 不证明唯一原因；冷却语义另看证据。
发出施法调用？hero.cast(spellName)调用、返回值与实际效果是三件事。
三个读取入口 JavaScript
var ownCollectors = hero.findMyCollectors();
var fireMana = hero.getTotalMana("fire");
var incomingMissiles = hero.findEnemyMissiles();
仅说明接口，不是完整策略；没有打印、对局执行或实测效果声明。

不要用曾在简介中出现的 hero.collectors 替代有效入口：历史逐字段探测发现它的属性读取会被拦截。

03

KEEP YOUR CLAIMS HONEST

三种说法，三种标签

文档说明

“简介这样写。”

保留页面与版本。说明值是线索，不自动变成实测值。

观测证据

“这一局，这一帧。”

需要 runId、源码身份、帧与错误检查，不能外推所有对手。

策略假设

“更多果农可能更好。”

考虑生成阻塞与收入，设计对照，而不是直接宣布最优。

unknown、估计值与样本不足不是需要藏起来的瑕疵，而是你下一次实验的起点。基础收口也不等于所有机制都已测定。

04

CHECK YOUR UNDERSTANDING

先作判断，再看解释

三个小问题，全部在本地判断。不上传、不保存，也不代表程序实战成绩。

Q1查询水元素法力，应使用哪一个入口？

Q2护盾消失时恰好有飞弹落地，能宣布它“到期”吗？

Q3“多造果农可能更好”，现在应该标成什么？

教师提示与延伸问题

单池查询要传对应元素；盾消失要区分被打碎与自然到期；更多果农的收益要和阻塞成本一起比较。

延伸：果农从列表消失，为什么不能只凭列表变化判断死亡原因？考虑观测缺失、身份、生命和伤害帧。

到官方页面验证时，先读共享约束，重进后点击右下角“开始”，只运行不评分；从 world.frames 观测，不把 print 放进策略。
